# Linux Permissions, Process Signals & Cgroups

Understanding Linux process states, POSIX permissions, Access Control Lists (ACLs), and Control Groups (cgroups v2) is vital for debugging container runtimes and Kubernetes pods.

---

## 🛡️ POSIX File Permissions & Access Control Lists (ACL)

### 1. Octal & Symbolic Permissions
- `r` (Read = 4), `w` (Write = 2), `x` (Execute = 1)
- Special bits:
  - `SUID` (4000): Process executes with file owner's privileges.
  - `SGID` (2000): Files created inside directory inherit directory group.
  - `Sticky Bit` (1000): Only file owner can delete file in shared directory (e.g., `/tmp`).

```bash
# [STATE-MODIFYING] Set SGID on shared ops directory so all created files inherit the group
chmod 2775 /opt/shared-scripts
```

### 2. Fine-Grained Permissions with POSIX ACLs (`getfacl` / `setfacl`)
When standard user-group-other permissions are insufficient:

```bash
# [READ-ONLY] View active ACLs on a directory
getfacl /var/log/app/

# [STATE-MODIFYING] Grant specific user read/write access without changing primary ownership
sudo setfacl -m u:deployuser:rwx /var/log/app/

# [STATE-MODIFYING] Set default ACL for future files created in the directory
sudo setfacl -d -m u:deployuser:rwx /var/log/app/
```

## 🚦 Process Signals & Lifecycle

Containers and orchestrators rely on POSIX signals to manage workload lifecycles:

| Signal | Number | Name | Action & Purpose |
| :--- | :--- | :--- | :--- |
| `SIGHUP` | 1 | Hangup | Reload configuration without terminating process. |
| `SIGINT` | 2 | Interrupt | Generated by `Ctrl+C`; requests graceful interrupt. |
| `SIGQUIT` | 3 | Quit | Graceful quit with core dump generation. |
| `SIGKILL` | 9 | Kill | Uncatchable immediate kernel termination. |
| `SIGUSR1` | 10 | User 1 | Custom application action (e.g., log rotation in Nginx). |
| `SIGTERM` | 15 | Terminate | Standard graceful shutdown request (used by `docker stop` and `kubectl delete pod`). |

### Testing Graceful Termination
```bash
# [STATE-MODIFYING] Send graceful termination signal
kill -15 <PID>
```

## 📊 Linux Control Groups (Cgroups v2) & OOM Killer

Kubernetes memory and CPU limits are implemented directly via Linux kernel cgroups v2.

### 1. Inspecting Cgroup v2 Hierarchy
```bash
# [READ-ONLY] Verify whether host runs cgroup v2
stat -fc %T /sys/fs/cgroup/
# Output must be: cgroup2fs

# [READ-ONLY] Inspect memory limits and usage for a container cgroup
cat /sys/fs/cgroup/system.slice/containerd.service/memory.current
cat /sys/fs/cgroup/system.slice/containerd.service/memory.max
```

### 2. Diagnosing Out-Of-Memory (OOM) Killer Invocations
When memory demand exceeds limits, the kernel's OOM killer invokes `kill -9` on the highest score process:

```bash
# [READ-ONLY] Search kernel ring buffer for OOM killer invocations
sudo dmesg -T | grep -E -i "oom[-_]killer|out of memory"

# [READ-ONLY] Inspect a process's OOM score badness rating (higher = first to be killed)
cat /proc/<PID>/oom_score
```
